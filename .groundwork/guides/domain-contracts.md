## Product boundary

The native Rust/GPUI client, Bun/TypeScript service and CLI share a monorepo with independent versions/builds. Bun SQLite owns persistent project/task/document/configuration/workspace state plus compiled run snapshots, questions, integration links and receipts. The service implements configured task pickup, local/Strands harness execution, explicit GitHub/Linear synchronization and optional containment. Native factory editing adapts React Flow algorithms/interactions into GPUI with MIT attribution. Client actions use the versioned API; stored records and capability support remain distinct from observed execution, authentication and environment readiness.

## Karabiner model

- **Project**: stable ID, name, kind `standalone | github | linear`, local root/repository reference, optional external connection metadata. A Linear-backed project can still reference a GitHub repository; issue source and code location are distinct. Store connection identifiers, not credentials.
- **Project configuration**: revisioned JSON containing workflow definitions, ordered stage definitions, agent definitions, instruction/skill references and task status definitions. Give every definition a stable ID; stage references use agent IDs and return-stage IDs. Store declarative data only. Configuration editing must not import or execute arbitrary TypeScript hooks.
- **Task**: durable work item with project/title/description, board status, optional workflow/stage/agent IDs, due date, ordering, subtasks and revision. Board status, current stage and execution state are distinct. `task.agentId` is operator assignment/context; stage agent IDs determine execution. `task.stageId` can choose a captured starting stage. Explicitly enabled scheduling may pick up eligible task edits.
- **Run**: execution ID, task/project identity, captured project/task/config/factory, state, timestamps and optional `retryOf`. Stage visits and actual agent invocations have their own IDs and observed outputs/metrics. Retry creates another run under the same task. Waiting questions survive restart; interrupted running effects require operator review.
- **Intervention/guidance**: runtime questions are addressed by run/question ID and resumed through their answer endpoint. Run instructions queue for the next agent invocation with explicit delivery markers. Legacy free-standing intervention records retain their separate note/intent semantics.
- **Document/artifact**: persisted project document with optional task association, kind, title, revision and typed content. Code tours retain ordered chapters, Markdown/diagrams/code/diffs and source references. Generated run artifacts link document IDs from the run and include run/factory/source provenance in their content; authored documents remain independent. Unknown additive block fields survive independent client updates.
- **Workspace tabs**: persisted ordered tabs, active tab ID and bounded recently-closed stack. Each tab has its own ID and a tagged stable target (`project`, `task`, `document`, `review`); review targets must identify the reviewed task/document and source revision when applicable. Keyboard switch/close/reopen uses this shared state. Persist it as namespaced client settings; no extra orchestration-workspace entity is required. Missing/deleted targets show an unavailable state and remain closable.
- **Harness/runtime metadata**: distinguish installed, authenticated, supported and unknown. Claude/Codex/Copilot/custom local adapters reuse their own authentication; the opt-in Strands adapter has a separate provider/model path. Target is independently host, MXC process sandbox or Apple-container Linux guest. Installed discovery alone does not prove authentication or guest readiness.
- **Statistics/templates**: stored counts and observed run duration/outcome/usage are available; missing cost/tokens remain unknown. Onboarding templates are editable declarative factories/document starters, compiled and executed only through the service's explicit dispatch or configured pickup.

## Minimal workspace and storage

Implemented boundaries: `apps/client/` (GPUI), `crates/protocol/` (Rust wire models), `packages/service/` (`karabiner-service`), `packages/cli/` (`karabiner`), and `packages/contracts/` (TypeScript wire types). Root Cargo and Bun workspaces coexist. Service and CLI each compile/version independently; neither is embedded into the desktop release contract. No generic plugin system or orchestration framework is needed.

Use `bun:sqlite` directly, one service-owned database at an explicit app-data path with a fixture override. In addition to projects/tasks/documents/config/settings/interventions/activity, schema 3 stores runs, scheduler pickup, run/session blobs, external task links and integration operation receipts. Foreign keys, transactions and stale-edit conflicts enforce the boundary. Active runs must be cancelled before deleting their owning records. Client and CLI never open SQLite directly; service-owned transactional schema upgrades preserve the independent storage version.

Current official Bun documentation supports synchronous prepared statements, transactions and WAL. Use strict bound parameters, `PRAGMA foreign_keys = ON`, WAL and bounded busy handling; keep network/other awaited work outside transactions. Bun uses Apple's SQLite on macOS, so avoid assuming bundled SQLite extensions or newest SQL features. Explicitly close the database on graceful service shutdown. Documentation: [SQLite](https://bun.com/docs/runtime/sqlite).

## Versioned transport and CRUD surface

The approved implementation uses HTTP/1.1 + JSON on `127.0.0.1:43173`, configurable by explicit port/URL. Bun serves it and native Rust/Bun CLI use ordinary HTTP. Persistent SQLite data is independent from the listener lifetime. Requests use bounded bodies and explicit JSON validation. API details are centralized in the contract's `ENDPOINTS` table. [Bun server](https://bun.com/docs/runtime/http/server). Initial Unix-socket research remains an evaluated alternative, not the current transport.

| Surface | Initial behavior |
| --- | --- |
| `GET /health`, `GET /v1/meta` | Service health; product version; supported API majors; capability list; storage availability. Stable bootstrap metadata lets incompatible clients explain the mismatch. |
| `/v1/projects`, `/v1/projects/:id` | Real list/create/get/update/delete with explicit associated-data deletion semantics. |
| `/v1/tasks?projectId=`, `/v1/tasks/:id`, `/v1/tasks/:id/comments` | Persisted tasks, status/stage edits, subtasks, due/order and operator comments. Explicitly configured scheduling may pick up eligible records. |
| `/v1/documents?projectId=`, `/v1/documents/:id` | Markdown/code-tour persistence, commit groups, diffs, review progress and revision conflicts. |
| `/v1/projects/:id/config`, `/v1/settings`, `/v1/workspace` | Workflow/agent/instruction/skill configuration, preferences and persistent workspace tabs. |
| `/v1/interventions`, `/v1/activity`, `/v1/stats` | Stored intervention intentions/questions/answers, activity and counts from stored state. |
| `/v1/events` | SSE ready/change invalidations; reconnect/focus refetches snapshots, without durable replay. |
| Factory/run/integration routes | `/factory` compile/export/import, `/tasks/:id/run`, addressed `/runs/:id` controls/instructions/questions and explicit project sync/task push. See the shared `ENDPOINTS` table and service guide for payloads. |

Separate API major from service/desktop/CLI semver and internal database version. Within `/v1`, additions are optional, existing meanings stay stable, unknown response fields are ignored/preserved, and clients should render a fallback for unknown enum/block kinds. Partial resource updates preserve fields an older client does not understand. Capability-check optional actions; incompatible majors fail visibly instead of requiring exact product-version equality. Use string IDs, UTC timestamps, safe numeric counts, and a consistent `{error:{code,message,details?}}` error body. Validate request bodies and provide 400/404/409/501 errors. Do not retry mutations automatically after an uncertain connection failure.

Use TypeScript DTOs/boundary validators and Rust Serde models against the same wire contract. The compiled service/CLI smoke exercises persistence, stale revisions and unsupported capabilities. A large schema/code-generation framework is unnecessary. SSE invalidations advertise `capabilities.events: true`; plain CRUD does not require an event bus or durable event log.

CLI initial commands: `--help`, `--version`, `service serve` (explicit foreground lifecycle), `status --json`, and thin project/task/document/config/settings CRUD commands through the same HTTP API. `node:util.parseArgs` is sufficient. Add no automatic login, daemon replacement or install flow. The [Bun argument guide](https://bun.com/docs/guides/process/argv), [workspaces](https://bun.com/docs/pm/workspaces), and [standalone executable guide](https://bun.com/docs/compiler/executables) cover this without runtime dependencies. `bun build --compile` supports `bun:sqlite` and separate macOS executables; runtime data must remain outside the binary.
