# Implemented factory contracts

Status: implemented and accepted, 2026-11-25, with exact GUI/API/CLI/SDK scopes and untested live prerequisites in the [capability matrix](factory-capabilities.md). `packages/contracts/src/{index,factory-types,factory-validation,factory}.ts` and owning adapter interfaces remain authoritative. Consumers use these contracts rather than the previous serial-only or guessed SDK shapes.

## Preserved boundary

The service owns SQLite, immutable run/factory snapshots, scheduling and executable semantics. GPUI and CLI share additive API major 1 DTOs. Factories remain declarative JSON bundles, with layout separate from executable identity; no arbitrary TypeScript evaluation or second client-side execution engine. `task.agentId` remains assignment/context, and stages own actual ordered agents. Existing serial factories, custom v1 JSONL, authored documents and workspace data require compatibility.

## Structured execution — core owner

- `WorkflowGraph.forks?: WorkflowFork[]`; a fork has `id`, source `stageId`, `branches: {id, entryStageId}[]` and `joinStageId`. Compiled workflows retain the same fork data.
- Execution uses structured, disjoint branches and a join-all boundary, with nested scopes and exactly-once join identity. Branch effects use the configured root/context; stage `cwd`, `executionTarget` and `targetOptions` are explicit overrides, not an implicit workspace/merge system. Aggregation exposes `activeStageIds` and sets `currentStageId` only when one stage is active; a run remains running while another branch works even if a sibling awaits input. Native pending-request UI remains reachable in that state.
- `RunExecutionState` contains durable `RunToken[]` and `RunScope[]`. Invocation IDs, token/scope IDs and `RunStepAttempt` distinguish concurrent visits and retry attempts. UI trackers and questions must not key solely by stage definition ID.
- `StageExecution` and commands accept bounded `retries`/`retryDelayMs`; retry count means extra attempts. Denial, cancellation and shutdown are excluded. Scoped returns, aggregate run state and interrupted-attempt recovery use the shared runtime contract and retain their accepted backend evidence; no automatic reattachment or side-effect replay is implied.
- Confirmed post-completion adapter cleanup failure is classified as nonretryable `adapter_cleanup_failed`. The attempt retains the actual completed output, usage, session identity and cleanup phase details; cleanup failure does not re-run successful agent side effects. The targeted Copilot correction proves one attempt/session and preserved seven-token output through this path.

## Interactive execution — core/harness/native seam

Copilot uses official `@microsoft/copilot-sdk` 2.0.3 with installed CLI1.0.116 (protocol4; SDK minimum4), `options.runtime: RuntimeConnection.forSpawnedStdio(...)` and `github.useLoggedInUser`. Targeted cases, compiled readiness and one actual live tool/permission/guidance run are accepted. The old `@github/copilot-sdk`1.0.34/max-protocol3 path failed negotiation before inference; that retained failure was compatibility, not authentication loss.

- `RunQuestion.kind` adds `permission`; interaction records expose provider/request IDs, stage-invocation/token identity, `transport: live | checkpoint`, choices, payload and typed response.
- Adapter requests add `interact`, `onSession`, `registerControl`; an `AdapterControl` declares permission/question support and steering mode (`native-turn`, `native-tool-boundary`, `next-step`) and implements steer/abort.
- `RunInstruction.deliveries[]` records actual mode, invocation and delivery time. Registering a control or storing guidance is not delivery. A live answer must settle its existing waiter rather than enqueueing a duplicate agent invocation; lost live sessions need explicit recoverable state.
- **Public response:** `{choice?: string, answer?: string, answers?: Record<string,string|string[]>, value?: Json}`. Native and CLI use this shared shape. Permission choice IDs come from the actual pending request, not a hard-coded allow/deny enum.
- Typed elicitation is normalized/validated by `runtime.answer` before persistence or live resolution. Number/integer metadata is preserved; native sends numeric/boolean/array JSON, invalid input returns400 with the request still pending, and the receiving SDK gets typed values (for example3, false and a multiselect array), not stringified substitutes.
- Installed CLI authentication and provider SDK identity are separate from configuration. Native permission decisions must use the provider's supported session channel, preserve the user's policy, and return explicit unsupported/error states when a prerequisite is missing. Do not silently substitute an approval gate, auto-allow policy or next-step queue for the requested live behavior.
- **Attempt correlation:** retries can reuse a logical step and providers/processes may reuse request IDs. An allow-once answer cannot be replayed into a different attempt/session merely because logical step/provider/request IDs match. Retained controlled cases exercise the implemented address/session boundary.

The inspected custom live bridge is explicit `AgentDefinition.protocol: "jsonrpc-v2"`; old `jsonl-v1` EOF behavior remains separate. `custom-bridge.ts` negotiates `initialize` with protocol `karabiner-harness-v2`, session identity and capabilities; `run` remains pending while the process may request `permission`/`question`. Permission choices declare offered IDs/labels and approve/deny/cancel **effects**. `instruction` returns factual `delivered`; `abort` and process settlement are owned. Drivers should use this landed handshake and `RpcProcess` framing, not retrofit v1 one-record stdin into a live channel.

## Native/controller and canvas seam

Canvas emits editing/navigation intent; native factory/config state owns domain history, IDs, clipboard/dependency remapping, revisions and service saves. Copy/Cut/Paste/Duplicate/Undo/Redo, context menus, keyboard reveal/Enter/Space, selection-box edges, lock/Esc, per-workflow `ViewportChanged`, Fork/Join kinds and app-local motion use that implemented seam. Retained source/GUI acceptance covers its scoped behavior. Edge auto-pan adapts React Flow's40px edge distance/15px-per-frame behavior. Clipboard IDs/internal references are remapped; disconnected copies require connection before executable validation. One-gesture history and viewport presentation do not manufacture config edits; programmatic echoes/SSE preserve drafts and the user-gesture auto-fit guard.

Native setup must expose existing integration/target configuration and the new fork/retry/permission fields without requiring JSON editing. The app-local Reduced Motion override is fixture-local; OS-global settings and user data/login are preserved. The [capability matrix](factory-capabilities.md) is the completion authority for user flows.

## Connected catalogs, refresh and target readiness

Connector/target ownership is `packages/service/src/integrations/**` and `runtime/targets.ts`; core owns public DTOs/routes and native/CLI consume them. The implemented catalog/readiness contract has scoped native/backend/CLI acceptance:

- `IntegrationService.catalog(projectId)` → `IntegrationCatalog`, through `GET /v1/projects/:id/integration/catalog`. Result carries provider/project, named `source`, teams with named states/suggested task statuses, named single-select `statusFields` with options, writable fields and `checkedAt`. Reads are explicit/paginated. GitHub repo uses a named source; Projects v2 exposes its single-select fields. Linear push maps remain keyed by team ID, and project URLs normalize their terminal 12-hex slug ID for lookup. Users select names; config stores existing IDs/maps. Catalog reads use the saved connection, so native setup saves the connection before loading mappings. Missing credential status exposes `credential_env_missing` and the environment name, never its value.
- Repository catalogs expose synthetic field `issue-state` / “Issue state” with stable REST choices `open` / “Open” (suggested todo), `completed` / “Completed” (suggested done), and `not_planned` / “Not planned”. These are REST state/reason mappings, **not ProjectV2 field IDs**; `statusFieldId` is used only for project scope. The common native mapping UI may show these labels and store their choice IDs in repository pull/push maps. Defaults remain todo/open and done/completed; an explicit not-planned pull mapping is honored.
- Project/Linear readback first uses an explicit pull mapping. When that mapping is omitted, a **unique explicit** push mapping may be inverted so a selected review-state push reads back as the intended task status. Ambiguous push maps are not guessed. This preserves explicit pull precedence and does not enable automatic publication.
- Publication selection is `input.fields ?? config.pushFields ?? ["title","description"]`, resolved only when a new operation is created. Project `integration.pushFields` uses catalog-writable choices; an explicit empty array is valid configuration but a new publication then fails with `publish_fields_empty` (409) before transport. Explicit input fields override policy. Stored operations keep their resolved fields/values across later policy or task changes. Native SourceLink captures the original body/request ID before dispatch and retains both across uncertain results or transport errors; a newer local revision must not silently rewrite that retry request.
- Finished receipts return before current task-revision checks. Pending original requests reuse their saved snapshot; another request ID is refused while any push for the task remains pending. Reconciliation attaches external metadata to the current local record without restoring stale title/status/revision. Deterministic pre-field failures and observed conflicts are resolved failures, not permanently pending operations; actual uncertainty still requires the original request ID.
- Provider uncertainty and a lost service HTTP reply are distinct paths: the backend fixture simulates a provider create accepted before its reply is lost; the GUI fixture must also reach SourceLink's transport-error path (for example, a local response-dropping proxy) before retrying the exact original body/key. Assertions inspect actual remote mapped values and retained local edits, not only mapping persistence or write counts.
- Both integration config variants gain `refresh?: {enabled, intervalMs?}`, default off; interval 30,000–86,400,000ms, default 300,000ms. `start()` is idempotent after successful service bind; deterministic `refreshDue(now?)` performs one automatic pull globally, respects manual project exclusion and always preserves local edits. Operations have a 120-second total signal bound. No automatic publication. `close()` stops timers, aborts/drains requests. `IntegrationInfo.refresh` reports enabled/interval/running plus optional attempt/success/next/error observations in memory; no schema migration is proposed.
- `targetReadiness({target, projectRoot?, targetOptions?, purpose?, executable?, check?, signal?})` → `TargetReadiness extends ExecutionTargetInfo` with `installed`, `configured` and `{code,path,message,status: passed|unknown|failed}[]` checks. Confirmed route is `POST /v1/projects/:id/execution-target/check` with `{check?,purpose?,executable?,config?,projectRoot?}`. `config` is a validated draft `ProjectConfig`; optional `projectRoot` supports the native unsaved-root check and is validated as nonempty/≤4096 characters before target readiness validates the directory. Omission uses the saved project root.
- `check=false` validates local settings/prerequisites; `check=true` may perform non-mutating MXC dry-run or Apple service/image inspection. It never starts a VM/harness or treats host login as guest authentication. Existing launch cwd/signal/fd3/cleanup contracts remain intact.
- The native draft-root override is now present in `server.ts`. It does not add a CLI rootPath flag; the documented CLI saved-project check remains unchanged.
- Target readiness uses MXC `--dry-run` with fd3 policy and Apple system status/image inspect only. GUI options produce MXC policy without requiring a profile file. Environment references resolve in memory; duplex stdin remains intact. Apple mount source aliases are canonicalized/deduplicated, read-only wins on duplicate sources and nested destinations remain under the fixed guest root. Resource validation follows the inspected Apple 1.7.1 implementation: CPUs cannot exceed host count; memory is at least 200MiB and accepts decimals/binary suffixes, including MB/GB parsed as binary. Do not substitute an arbitrary 128-CPU cap or integer-only memory parser for target checks.

## CLI interaction contract

Implemented CLI operations use the shared public DTOs:

```text
question show QUESTION --run RUN
question answer QUESTION --run RUN --choice OFFERED_CHOICE_ID [--revision N]
question answer QUESTION --run RUN --file response.json [--revision N]
question answer QUESTION --run RUN --file -
targets [show ID] [--project PROJECT]
targets --project PROJECT --check [--purpose command|harness] [--executable NAME] [--file config.json|-]
harnesses [show ID]
harnesses check --file agent.json|- [--project-root PATH] [--check]
harnesses check --project PROJECT --agent AGENT [--check]
```

The response file is the full `AnswerRunQuestion` body, forwarded unchanged apart from an explicit nonconflicting revision. Text/`--message` retains exact `{answer}` behavior; mixed response inputs fail locally. Example multi-field body: `{"answers":{"summary":"Ship the reviewed work","checks":["tests","audit"]}}`. Provider-schema values use `{"value":{"providerField":"value"}}` only when the offered schema matches. `question show`/human list expose actual kind/prompt/choices/payload/provider/transport/invocation IDs. Existing run/factory show retain raw forks/tokens/scopes/attempts/deliveries.

**Final target CLI correction:** plain target discovery remains GET `/v1/execution-targets?projectId=...`. `targets --project PROJECT --check` submits exactly one POST to the configured project's `/execution-target/check` with `{check:true}` plus optional `purpose`, `executable` and `config` from `--file`/stdin. It returns the complete `TargetReadiness` object; unavailable/failed checks set exit 1 without discarding diagnostics. `show ID --check`, `--check` without project and contradictory options fail locally. There is no rootPath override, login or auto-install. The driver must assert this POST body/reply, not the superseded suggested GET check query.

**Harness readiness:** POST `/v1/harnesses/check` accepts `{agent,check?,projectRoot?}` and returns full `HarnessReadiness` (`code`, optional credential **environment name**, supported permission/question/steering capabilities and checks). CLI file/stdin mode posts the full agent with explicit `check:false` unless `--check` is supplied; saved-project mode reads the actual agent and project root first. Unknown authentication alone remains a successful diagnostic response; unavailable/error/failed checks set exit 1 without discarding data. Known-provider `check:true` uses bounded non-mutating authentication status only (Claude auth status, Codex account/read with refreshToken false, Copilot SDK getAuthStatus); it creates no model thread/session. Custom readiness never executes the configured process, and Strands readiness checks environment references without a network call. Plain harness list/show does not accept the check/project options.

File/stdin harness checks accept explicit `--project-root PATH`, forwarded byte-for-byte as `projectRoot` with no file-directory inference. It is file-mode only; saved-agent mode uses the stored project root. Native checks also pass the current nonempty draft/saved workspace root. Relative executables must resolve against that root even when `check:false`, not against the service's working directory. The added fixture uses `./bin/agent`, a real owned root and a launch sentinel that must remain absent.
