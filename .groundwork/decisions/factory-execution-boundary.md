# Service-owned factory execution and native visual configuration

Status: accepted implementation boundary, 2026-11-25. Supersedes the execution-deferral portions of the earlier local/client service records. The graph/runtime/integration contracts are implemented; isolated compiled runtime assertions have been observed, while live-provider/containment and final native visual evidence remain separately qualified.

Related decisions: [local service boundary](local-service-boundary.md), [native client and service boundary](client-service-boundary.md), accepted [native factory canvas](native-factory-canvas.md).

**Feature-completion successors accepted.** The user's subsequent parallel fork/join, bounded automatic retries, native provider permissions and active-session guidance requirements are implemented and accepted. [Structured execution](structured-factory-execution.md) and [live interactions](live-harness-interactions.md) are the current successors; the [capability matrix](../guides/factory-capabilities.md) records scoped GUI/API/CLI acceptance. The earlier single-path/retry-zero/queued-only behavior remains baseline history, not the current limitation.

## Context

The existing accepted boundary intentionally implements persistent CRUD/configuration and intervention intent while leaving scheduling, harness execution, project synchronization and optional containment as extension points. The user's new instruction is to build the remainder of the service and a drag/drop, configurable/linkable factory in the client, compiling to a definition similar to [Buckle's examples](https://github.com/darylcecile/buckle/tree/main/example) and executing through the service. The user clarified that React Flow should inform a native GPUI port, avoiding a webview. The original native Rust/GPUI client, independently versioned Bun service/CLI and service-owned local SQLite remain relevant requirements.

The initial implementation had an empty run read model and stored workflow/stage/agent configuration. `apps/client/src/views/workflow/config.rs` already owned revisioned native configuration drafts, and the user had added `@strands-agents/harness: ^0.5.0`. Those existing boundaries motivated extending the service's authority and native draft model rather than adding another scheduler or client persistence layer.

## Decision

1. The Bun service owns validation/compilation, factory scheduling, task dispatch, execution lifecycle, run persistence, adapter invocation and operator delivery. SQLite remains the local source of truth; the native client and CLI use the additive API major 1 boundary and can update independently. Compilation is pure declarative snapshot construction. The delivered `FactoryBundle` is `karabiner-factory` version 1 JSON: editable `config.json` retains layout, normalized `factory.json` captures execution, and related JSON modules expose workflows/stages/agents/instructions/skills. Export/import consumes data rather than importing/evaluating executable TypeScript callbacks.
2. A native GPUI graph canvas supplies visual editing within the project workflow, adapting React Flow's relevant MIT-licensed algorithms/interactions with attribution. The saved factory is declarative, inspectable and executable by the service; graph edits and compiled execution share one defined meaning, including actual branching and return paths. Layout is separate from execution edges. The client is not a second execution engine and uses its existing native API/draft boundary.
3. Configured agents execute through supported interfaces to locally installed/authenticated Claude, Codex, Copilot or a custom harness. Strands `createHarness` provides an adapter seam where appropriate, not a second graph scheduler. Local CLI model identifiers remain distinct from Strands provider/model identifiers; Strands has no Copilot provider alias. Its presence does not imply a mandatory cloud-provider credential flow.
4. Tasks remain work items, separate from durable run attempts and concrete stage/agent invocations. Run output, provenance, observed metrics and intervention delivery states describe what actually occurred. Optional containment and source integrations expose real prerequisite/capability results rather than synthetic execution success.
5. Preserve revisioned existing data, unknown additive fields and authored documents/tours. Configuration retains references rather than plaintext credentials. The implementation and its verification reuse the user's existing environment and authentication.
6. Stage execution follows before commands → ordered agents → stage commands → gates → after commands. Success/failure have one successor; explicit structured forks provide concurrent branches/join scopes. Multiple return destinations use an explicit target and visit/transition bounds. `task.agentId` remains assignment/context; ordered `stage.agentIds` preserve actual executing agents/reviewers. A captured `task.stageId` may select the start stage without fabricated predecessors. Bounded stage/command retries preserve attempt history and exclude denial, cancellation, shutdown and confirmed post-completion cleanup failures. Waiting checkpoints survive restart; interrupted active work requires explicit recovery rather than automatic replay. Harness choice is independent from host/MXC/Apple target, and a macOS CLI/keychain is not implicitly available in a Linux guest. Subscription access does not establish API cost.
7. Addressed instructions reach active supported adapters at their declared native-turn/tool boundary, with attempt-scoped delivery receipts. A next-step fallback remains explicitly deferred; instructions also remain cumulative for later invocations. Typed question/permission responses resolve the existing addressed waiter rather than duplicating an invocation. These implemented channels supersede the baseline queued-only guidance restriction.

## Runtime and integration ownership

Installed `@strands-agents/harness 0.5.0` and SDK `1.26.0` are the API authority rather than the site's older version footer. `runtime/strands-adapter.ts` uses actual `createHarness`, file/shell/skill tools, cancellation/shutdown and session storage backed by `run-store.ts`; the service's `scheduler.ts`/`pipeline.ts` own the graph. Local adapters use explicit executable/argument protocols and existing authentication. Claude's permission-prompt suppression requires CLI 2.1.259+.

The SDK's provider/intervention peer packages are explicit pinned service dependencies so standalone Bun compilation resolves its conditional imports. They are bundled with the independent service; adding them does not authenticate a provider or cause a model call. No build externalization or alternate execution entrypoint is used.

`integrations/service.ts` uses explicit lazy-status/pull/push operations, preserves local edits by default, retains deletion tombstones and reconciles uncertain creation by request ID. `runtime/targets.ts` owns host/MXC/Apple context and prerequisite handling, with MXC configuration on fd 3 and uniquely named Apple cleanup. The [service guide](../guides/service.md) documents the concrete wire protocols and [native canvas decision](native-factory-canvas.md) owns the client seam.

The compiled storage/runtime journeys exercise real local process effects and a real Strands harness driven by a scripted model. Injected connector/target fixtures separately establish mapping, receipts and invocation/cleanup contracts. Installed package presence or those fixtures alone does not establish live provider authentication or actual containment. Run evidence records both assertion outcomes and any whole-tree source freshness limitation; architectural acceptance is not a fabricated fresh pass receipt.

## Consequences

- The earlier execution deferral is no longer the implementation task's scope, but capabilities must advance only when backed by working behavior. Environment-limited live exercise remains explicit.
- A focused factory-runtime journey and native graph-builder journey can establish the new boundary using the repository's existing isolated smoke pattern. Actual native visual review is necessary; compile/source assertions alone cannot establish interaction or visual quality.
- The native app/service, local login, data and unrelated formatting/lint/dependency changes remain user work. Test drivers may own temporary fixture processes and databases; that does not authorize restarting or replacing the user's instances.

## Adoption

The earlier storage/transport and independent native/service/CLI version decisions remain valid. Their deferred-execution statements are retained as history and linked here. Runtime and native evidence stay in their own verification records, including environment and source-freshness gaps, rather than being inferred from this decision.
